# Block Map — журнал решений

Формат: что решили, почему, что из этого следует. Открытые вопросы в конце.

## Шаг 1. Словарь сущностей

### D0. Терминология (решено)
| Термин | Что это | Пример |
|---|---|---|
| **Сценарий** | Логическая схема по слоям: блоки в дорожках и стрелки потока данных между ними. Уровень 1 | «Озвучка», «Баланс и оплата» |
| **Блок** | Узел в дорожке слоя. Клик раскрывает его блок-схему. Уровень 2 | «Позиция чтения (bookStore)», «AudioManager» |
| **Блок-схема** | Классическая схема внутри блока: овал начало/конец, ромб условие, прямоугольник действие, параллелограмм данные. Уровень 3 | внутренности `AudioManager` |
| **Общий ресурс** | Файл, стор, база, используемые несколькими блоками и сценариями. Показывается внутри блок-схемы как «читаем/пишем отсюда» | `bookStore`, `db.audioCache` |

Раньше в разговоре слово «блок» означало сценарий целиком (например, «Озвучка»). Дальше использовать только термины из таблицы.

### D1. Слои — пять дорожек (решено)
UI · State · Domain · Data (внутренние данные: Dexie, серверный JSON) · Infra / External (внешние API, TTS-провайдеры, ЮKassa, Tauri IPC, proxy).
Зачем отдельный Infra: сразу видно, где работа идёт с внешним миром (сеть, ключи, деньги).

### D2. State и кто им управляет (решено, формулировка)
- State только хранит данные, сам ничего не запускает.
- Локальное состояние компонента (нажата ли кнопка) остаётся в UI.
- Состоянием приложения управляет управляющая функция из Domain: UI отправляет команду, Domain обновляет State и запускает процессы.
- Следствие: domain → state допустимо (записывает); state → domain подозрительно (стор тянет логику); прямая запись в стор из UI в обход команд подлежит разбору.
- Матрица допустимых связей между слоями **не решена**.

### D3. Структура сценария (решено, заменяет прежнюю версию)
- Сценарий показывает блоки в дорожках слоёв, между блоками стрелки потока данных («что и зачем происходит»).
- Стрелки внутри сценария, а не по всему проекту, поэтому «лапши» нет.
- Блок раскрывается в блок-схему (уровень 3).
- Прежняя запись «связей между блоками нет, блок = логическая цепочка без стрелок» отменена: она смешивала уровни 1 и 3.

### D4. Общий ресурс (решено)
- Не блок и не узел сценария. Показывается внутри блок-схемы блока как шаг «читаем/пишем отсюда».
- По клику виден список «кто ещё читает и пишет этот ресурс» (реестр ресурсов).
- Правка ресурса сразу показывает, какие блоки и сценарии затронуты.

### D5. Что автоматика, что человек/LLM (следствие D3, D4)
- Авто: слой блока по пути файла, якорь `файл:строка` и символ, реестр ресурсов и потребителей, хеши ресурса и якорных символов, блок-схема функции из AST (ветвления, циклы, вызовы, вход и выход).
- LLM/человек: состав сценария (какие блоки входят, какие стрелки), названия, подписи шагов блок-схемы, описания.
- Нарезка кластеризацией по графу импортов для этой модели не подходит: блок это логическая единица, а не набор файлов (F1 0.45 по папкам, 0.39 по графу). Задача 1.4 в Secretary требует пересмотра.

### D6. Библиотека блоков (решено)
- Блок может входить в несколько сценариев (например, `AudioManager` в «Озвучке» и в «Чтении»).
- Блок самостоятельная сущность в библиотеке проекта: стабильный id, слой, якоря, порты входа и выхода, блок-схема. Сценарий хранит ссылки на блоки и стрелки между ними.
- При клике на блок подпись «входит в сценарии: …» вычисляется из ссылок.
- Правка блока показывает затронутые сценарии; хеш блока помечает их как требующие проверки.
- Новый сценарий можно собрать из существующих блоков; агент ищет в библиотеке и создаёт только недостающие блоки. Совместимость блоков проверяется по типам портов.
- Риски: блок ведёт себя по-разному в разных сценариях (параметры или варианты блока), версионирование контрактов становится критичнее (0.3), нужны строгие типы портов.

### D7. Чистые фиксированные блоки и функции, переносимость (решено, закрывает вопрос о параметрах)
- Блок это фиксированная единица с закрытым контрактом. Нужен другой вариант, создаётся другой блок; параметры-как-варианты не вводим.
- Блок-схема блока состоит из функций; функции переиспользуются в блок-схемах других блоков.
- Три уровня библиотеки с контрактом и версией: функция → блок → сценарий. Переносить можно любой уровень, в том числе в другой проект (пример: сценарий оплаты ЮKassa).
- «Чистый» понимается как **закрытый контракт**: блок заявляет входы, выходы, побочные эффекты (чтение/запись БД, сеть) и зависимости. Математическая чистота не требуется (AudioManager пишет в Dexie, ЮKassa ходит в сеть).
- Переносимость обеспечивается портами и адаптерами: блок объявляет нужные порты (хранилище, HTTP-клиент, конфиг), проект подставляет реализацию. Иначе блок тянет за собой `db.ts` и сторы конкретного проекта.
- Опубликованный блок неизменен; правка даёт новую версию, сценарии ссылаются на конкретную версию (связано с 0.3).
- Уровень чистоты блока (метка): чистый / эффекты заявлены / запутан (напрямую использует глобальные сторы или базу). Это метрика переносимости и список рефакторинга. Карта сначала описывает существующий код, поэтому часть блоков будет «запутана».
- Риски: размножение блоков (нужен поиск и контроль дублей), стоимость рефакторинга существующего кода под порты.

### D8. Схемы в манифесте, языковые адаптеры (решено)
- Типы портов: схема (сигнатура) плюс короткое смысловое описание **только на границах блока**.
- Порты-зависимости (хранилище, HTTP, конфиг) описываются **схемами в манифесте**: язык-нейтральный источник правды (для будущих языков).
- Для TS-проектов интерфейсы формируются из манифеста (генератор); обратное направление (манифест из существующего кода) используется для первичного заполнения.
- Языковой адаптер состоит из трёх частей: генератор (манифест → интерфейсы в коде), экстрактор (код → сигнатуры, якоря, ресурсы, блок-схемы), раскладка слоёв (путь → слой).
- Планирование = манифест → генератор; автопостроение и сверка = код → экстрактор → сравнение с манифестом.
- Flutter/Dart как второй язык: порты это абстрактные классы, адаптеры подставляются через DI; экстрактор на пакете `analyzer` или tree-sitter; слои по папкам `presentation / domain / data`. Формат схем: JSON Schema для форм данных плюс собственное расширение для эффектов, зависимостей, слоя и версии (поддержку Dart в quicktype нужно проверить).

### D9. Чтение и запись ресурса (решено)
- Определяются автоматически по AST (вызов `set`, присваивание, `db.put` = запись, остальное = чтение).
- На этапе проектирования читателей заранее знать не нужно: при разработке они подтягиваются из кода сами.
- Ручная пометка в манифесте только для спорных мест.

### D10. Блок-схема: AST как факт, ручная схема как намерение (решено)
- Блок-схема функции строится из AST автоматически (факт). Рядом хранится упрощённая ручная схема (намерение, 8–12 шагов). Расхождение между ними сигнал.
- `try` на схеме остаются видимыми, `catch` без throw/return и `promise.catch`, который только логирует, помечаются как риск.
- Шум сворачивается правилами (console.*, проверки abort), без LLM.

### D11. Привязка по хешу кода (решено)
- Шаг схемы привязан к фрагменту кода хешем токенов (без пробелов и комментариев), а не номером строки. Ключ узла = хеш#номер повтора.
- Проверено: сдвиг строк, комментарии и переформатирование хеш не меняют; правка условия или нового оператора находится ровно в нужном узле.
- Состояния: код без шага схемы (новый или изменённый), шаг без кода, код шага изменился после утверждения (хеш не найден, предлагаются кандидаты).
- Утверждение (`build.mjs --bind`) фиксирует хеши кода и схемы. Дальше хеши блока и схемы показывают, актуально ли утверждённое состояние. Идея развивается вверх: хеши блоков в хеше сценария (пока не сделано).
- Ограничение: группа подряд идущих простых операторов хешируется целиком, добавление оператора меняет весь узел.

### D12. Раскладка «Озвучки» и «Чтения» (решено)
- Правила переходов плеера (`reducePlayer`) и словарь произношения это **функции**, а не блоки. «Статус плеера» (State) блок.
- Бывший AudioManager разделён: **Управление воспроизведением** (Domain), **Получение аудио** (Domain, кэш + синтез, самый переносимый), **HTML Audio** (Infra).
- **PDF-координатор** (Domain): готовность страниц, ожидание, приоритет распознавания. Плеер просит у него «следующую фразу» и не знает, что это PDF.
- UI: **Выбор экрана по типу файла** (единственное место, где UI различает типы) → **Читалка текста** или **PDF-экран** (оригинал + распознанное).
- Роутер провайдеров и OpenRouter один блок (детали в его блок-схеме).
- Ожидаемые находки сверки: логика управления воспроизведением живёт в `audioStore` (State), состояние может писаться раньше подтверждения.

### D13. Правила слоёв (ЧЕРНОВИК, ждёт подтверждения)
Формулировка пользователя, уточнённая:
- **UI**: команды только в Домен; отображает только по State; читает State, не пишет. Локальное состояние компонента остаётся в UI.
- **Домен**: единственный, кто выполняет работу. Читает State, пишет State (только свои куски), ходит в Data и Infra в обе стороны. Домен → Домен допустим.
- **State**: только хранит. Допустимы чистые селекторы и тривиальные `set`; persist (`localStorage`) явное исключение. Логика в сторе это логика в чужом слое (сейчас `audioStore`).
- **Data / Infra**: общаются только с Доменом. **Поток данных** двусторонний (результаты, события), но **зависимость в коде** односторонняя: Data и Infra не импортируют Домен, события приходят колбэками, которые регистрирует Домен.
- **Общие типы** (`types/`) можно импортировать из любого слоя.
- **Владение состоянием**: у каждого куска состояния ровно один блок-писатель (Домен), остальные читают. Проверяется автоматически.
- **Загруженная книга** (главы, предложения) это состояние (State); Домен читает её оттуда. Data хранит сохранённую книгу, загрузка из Data отдельный сценарий.
- **Виды блоков на схеме**: логика (код в любом слое, включая адаптеры Data/Infra), кусок состояния, хранилище данных. Состояния и данные это записи каталога, а не логика.
- Следствия для инструмента (не сделано): матрица слоёв в `zones`/`check` по ролям кода, каталог состояний с владельцем-писателем, три вида узлов на схеме.

### D14. Проверка плановой архитектуры по блок-схеме (сделано)
- `blockmap lint`: проверяет схему без кода. Правила: матрица слоёв на стрелках, запись в состояние только от владельца, «данные из ниоткуда» (блок пишет и вызывает, но ничего не получает), блок-схема блока согласована со сценарием (шаг читает/пишет/вызывает ресурс или блок, и на сценарии есть такая стрелка, и наоборот), шаг с данными называет источник (`res`, `block`, `via: input | external`).
- Запланированные блоки (`planned: true`): без якоря в код, стрелки к ним «план», не «кода нет». Первый: «Навигация по книге», владелец позиции чтения.
- Куски состояния связываются с блоками полем `slice` у State-блоков.

### D15. Блоки это роли (решено)
- Блок на верхнем уровне это **роль с ответственностью**, как сотрудник или поставщик в бизнесе. У роли своё состояние (владелец одного куска). Мелкие функции вложены в блок-схему роли, а не стоят на верхнем уровне.
- Роли «Озвучки»: **Координатор воспроизведения** (управляет поставками и ходом: получает команду UI, у Поставщика фраз берёт фразу, у Поставщика озвучки аудио, пишет позицию, поручает Оркестратору), **Оркестратор аудио** (только управляет Плеером и статусом плеера, с поставщиками не общается), **Поставщик фраз** (книга: текст и PDF), **Поставщик озвучки** (кэш + синтез у провайдера).
- Код блока должен лежать в слое блока. Если нет, это находка «не в своём слое» (сейчас: Координатор лежит в `audioStore` в State, Плеер внутри `AudioManager` в Domain).
- Путь вызова через чужой блок это обход, а не подтверждение связи (сейчас Оркестратор сам зовёт Поставщика озвучки вместо Координатора).

### D16. Правила составления схемы и версии (сделано)
- Правила одним документом: [block_map_rules.md](block_map_rules.md). Метафора: компания с отделами; всё строится вокруг зоны ответственности.
- Ответственный есть и у Data/Infra (ресурс с `owner`): к нему ходит только его отдел. Проверяется по коду и на схеме.
- Циклов вызовов между отделами нет (`lint`, ошибка).
- Версии схемы внутри вехи: `мажор.минор.патч`; `blockmap version` считает изменения структуры и подсказывает увеличение, `blockmap release` выпускает версию (снимок в `tools/blockmap/ui/releases/`).
- Агент-архитектор: [block_map_architect_prompt.md](block_map_architect_prompt.md) собирает схему по описанию функции.

### D17. Зоны ответственности (сделано)
- Вторая ось схемы: слои по горизонтали, **зоны** по вертикали. Блок в одной зоне; у зоны один глава; межзонные вызовы и записи только в главу (чтение состояния разрешено). Проверяется на схеме (`lint`, ошибка) и в коде (`check`, предупреждение «не через главу зоны»).
- Зоны читалки: Экран, Координация воспроизведения, Плеер, Поставка озвучки, Поставка фраз, Общая. «Воспроизведение» разделено на две: координация (что и когда играть, позиция) и плеер (управление плеером и статус).
- На схеме: цветные рамки зон, ширина зоны и высота слоя регулируются, блок не выходит за рамку зоны. `layout` подбирает порядок зон и колонки внутри зон.
- Находка кода: Координатор пишет статус плеера (`dispatch`) мимо главы зоны «Плеер».

### D18. Инструмент описан своей же картой (сделано)
- Профиль проекта (`--profile=<имя>`, `tools/blockmap/ui/profile.mjs`): корни кода, расширения, слои, где лежат модель и выходные файлы. Профили: `reader` (читалка) и `tool` (сам инструмент, карта в `tools/blockmap/profiles/tool/model.json`). Карта разбирает `.mjs`.
- Слои инструмента: UI — команды (`cli/`), Домен — сборка, проверки, правки карты, версии, раскладка, Data — файлы карты (`lib/store/`), Infra — адаптеры TypeScript (`callgraph`, `flowgen`, `importgraph`, `states`, `dead`).
- Зоны: Представление, Сборка карты, Проверки, Версии, Правки карты, Раскладка, Сбор данных. Вход в зону один: Сборщик карты, Проверки (`lib/checks.mjs`), Версии, Редактор карты, Раскладка, Поставщик фактов (`ui/facts.mjs`).
- Один писатель: `model.json` меняет только Редактор карты (`lib/editor.mjs`). Команды только разбирают аргументы и печатают.
- Проверка: `npm run blockmap:self` (check --strict на карте инструмента) и `npm run blockmap:test` (14 тестов).

### D19. Что нашла карта на самом инструменте
- Замысел с первого раза нарушал собственные правила: зоны с несколькими входами, Infra вызывает Infra (вход в зону «Сбор данных» должен быть Домен-поставщик), хранилище из трёх ролей без владельцев. Всё исправлено до кода.
- Код нарушал замысел: команды писали `model.json` и звали TypeScript-адаптеры напрямую (UI → Data, UI → Infra). Логика перенесена в Домен.
- Ошибка анализатора: граф вызовов не видел вызов, когда тело стрелочной функции само является вызовом (`() => f(x)`). Исправлено; у читалки каталог состояний теперь видит запись `theme` через `setTheme`.
- Правило ресурсов уточнено: ресурс можно объявить «читают все, пишет владелец» (`readers: 'any'`, `writePattern`); сам блок-хранилище нарушителем не считается.

### D20. Рефакторинг без изменения результата
- Перед правками снят эталонный вывод читалки (`check`, `lint`, `states`, `reality`, `zones`, `list`, `block`, `impact`, `model.computed.json`, `map.html`). После разбиения `build.mjs`, `blockmap.mjs`, `template.html` на модули вывод совпал побайтно; единственная разница — исправление из D19.
- `build.mjs` — функция `buildMap`, а не скрипт: команды вызывают её напрямую, без дочернего процесса. Страница карты собирается из `ui/view/*` (`ui/page.mjs`).

### Открытые вопросы шага 1
- Матрица допустимых связей между слоями (D2).
- Насколько подробна блок-схема из AST: функция целиком или только ключевые ветки.
