# Промпт для агента: разметка кода по карте блоков (только чтение кода)

Скопируйте блок «Промпт» целиком. Рабочая папка: корень проекта AIBookReaderWeb.

---

## Промпт

Ты размечаешь код проекта по карте блоков (Block Map). **Исходный код проекта не меняй и не форматируй.** Единственный файл, который ты правишь, это `tools/blockmap/ui/model.json`, и только перечисленные ниже поля. Твоя задача: описать, что каждый блок **должен** делать, привязать это к реальному коду и честно записать, где код не совпадает с замыслом.

### Карта
- **Сценарий** → **блоки** (в дорожках слоёв UI / State / Domain / Data / Infra) → **блок-схема** блока.
- Сценарии сейчас два: `sc_tts` «Озвучка» (про воспроизведение и состояния, про экраны и тип файла не знает) и `sc_read` «Экран чтения (UI)» (выбор экрана, экраны, откуда они берут данные).
- Блок может входить в несколько сценариев. Общие ресурсы (`resources`: сторы, таблицы БД) блок обязан заявить в `res`.
- Два вида блок-схем: **AST** (строится из кода сама, это факт) и **схема-намерение** (пишешь ты, 8–12 шагов, это замысел). Шаг намерения привязан к коду по хешу фрагмента, а не по номерам строк.

### Команды (из корня проекта)
```
node tools/blockmap/blockmap.mjs list                 # блоки, статусы, покрытие
node tools/blockmap/blockmap.mjs block <id>          # всё про блок (--json полностью)
node tools/blockmap/blockmap.mjs impact <файл[:стр]> # что заденет правка
node tools/blockmap/blockmap.mjs zones               # блоки в чужих зонах
node tools/blockmap/blockmap.mjs check               # актуальна ли карта (код 1 если нет)
node tools/blockmap/blockmap.mjs bind <id>           # утвердить блок или сценарий
node tools/blockmap/blockmap.mjs risks               # проглоченные ошибки по всему проекту (красные: ни throw, ни лога)
node tools/blockmap/blockmap.mjs ack <файл:стр> "причина"  # принять риск осознанно (сбросится при правке кода)
node tools/blockmap/blockmap.mjs declare [--apply]   # заявить блокам ресурсы, которые их файлы уже используют
```
Если задача про сам инструмент (`tools/blockmap`), добавляй `--profile=tool` к каждой команде: его карта лежит в `tools/blockmap/profiles/tool/model.json`, страница — `tools/blockmap/out/tool/map.html`. Быстрая проверка: `npm run blockmap:self` и `npm run blockmap:test`.
`lint` проверяет **плановую архитектуру** по схемам, без кода: слои на стрелках, владельцев состояний, «откуда данные» и согласованность блок-схемы блока со сценарием. Шаг с данными должен называть источник: `res` (ресурс или кусок состояния), `block` (блок), `via: "input"` или `"external"`. Предупреждения `lint` исправляй разметкой (добавь шаг, стрелку, источник), а не подгоняя замысел под код.
`states` печатает **каталог состояний**: куски состояния (`states` в model.json), владелец-писатель, кто пишет и читает, действия сторов с логикой других слоёв. Правило: пишет только блок-владелец, остальные просят его командой; запись не из владельца это нарушение. Куски и владельцев назначай в `states`, не меняя код.
`check` теперь сверяет и **стрелки сценариев с кодом**: для каждой стрелки между блоками ищет реальный вызов функции блока-получателя (или импорт стора). Нет вызова: `✗ ребро A -> B не подтверждено в коде`. Вызов идёт через чужой слой: предупреждение «в обход слоя». Блок, не достижимый от точки входа сценария (`entry`) по подтверждённым стрелкам, это «мёртвый блок на карте»; функция, которую никто не вызывает, «мёртвый блок в коде». Не подтверждённую стрелку нельзя «исправить» правкой схемы, если замысел верный: либо код переносится, либо расхождение принимается явно: `edge-ack <от> <к> "причина"`. Нужен ли блоку шаг блок-схемы под вызов, подсказывает поле `block` у шага намерения (`"block": "b_dom_fetch"`).
`check` печатает «подсказки»: например, что якорь AST выглядит как диспетчер (мало узлов) и в классе есть метод с настоящей логикой, или что схема не привязана к коду (нет `covers`). Читай их и исправляй разметку.
Карта в браузере: `tools/blockmap/out/map.html` (пересобирается любой командой).

### Что разрешено менять в model.json
1. `astFlows`: `"b_xxx": { "file": "src/…", "fn": "функция" }` (метод: `"Класс.метод"`).
2. `flows`: схема-намерение, узлы `{ "id", "t", "label", "col", "row", "covers": [[с, по]], "res", "rw" }`, `t` это `start | end | step | io | cond`; рёбра `{ "from", "to", "label" }`. У блока поле `"flow": "<id схемы>"`.
3. У блока поле `res` (заявленные ресурсы), при необходимости новая запись в `resources`.
4. Поля `bind` и `approved*` ставит только команда `bind`, `riskAcks` только команда `ack`. Руками не трогай.
5. Для классов в `astFlows` указывай метод с реальным телом логики, а не диспетчер из нескольких строк. Ресурсы блока можно заявить командой `declare --apply` (она не трогает нарушения).

### Порядок
1. `list`, `zones`: зафиксируй исходное состояние.
2. Блоки по очереди, начиная с Domain и Infra (`b_dom_audio`, `b_dom_fetch`, `b_dom_source`, `b_dom_pdf`, `b_dom_tokenize`, `b_infra_router`, `b_infra_audioel`), потом State, Data и UI. Для каждого:
   a. Прочитай код якоря и `block <id>`.
   b. Если логика блока это функция, добавь запись в `astFlows`.
   c. Нарисуй схему-намерение (8–12 шагов): что блок должен делать, а не пересказ строк. Шаг, которого в коде нет, но он нужен по замыслу, оставь с `"covers": []`.
   d. Проставь `covers` по реальным строкам. Логирование, проверки отмены и прочий шум в схему не включай.
   e. `block <id>`: посмотри «код без шага» и «шаг без кода». Каждое расхождение классифицируй: неточность схемы или проблема кода. Схему подгонять под код молча нельзя.
   f. Только после сверки: `bind <id>`.
3. Блоки без одной функции-якоря (экраны, сторы, таблицы) схем не требуют: проверь якорь, заявленные ресурсы и принципы ниже.
4. В конце `bind sc_tts`, `bind sc_read`, затем `check` и `zones`.

### Принципы (проверяй код на нарушения)
1. UI только отправляет команды и читает состояние. Бизнес-состояние сам не выставляет.
2. Состояние пишет только Домен и только после подтверждённого результата (`started`, а не «нажали Play»).
3. У ошибок есть путь: сбой Домена → статус `error` в State → UI показывает.
4. State только хранит данные, логики в сторе нет.
5. Infra (провайдеры) не знает про кэш и состояние: результат возвращает, кэш пишет Домен.
6. Сценарий «Озвучка» не знает про тип файла (текст или PDF): это скрыто за блоком «Источник следующей фразы».
7. Слои идут через Домен: UI → Infra/Data напрямую недопустимо.

### Чего не делать
- Не менять исходный код, не добавлять в него комментарии, не запускать форматирование.
- Не утверждать (`bind`) блок, пока не разобраны расхождения.
- Не выдумывать `covers`, не прочитав код. Не создавать новые блоки: если логика не вмещается, запиши предложение в отчёт.
- Не «исправлять» нарушения принципов: они пишутся в отчёт, а не в код и не в схему.

### Отчёт
1. **Сделано:** по каждому блоку: AST да/нет, шагов намерения, покрыто X/Y, утверждён да/нет.
2. **Расхождения:** код без шага схемы / шаг без кода (`файл:строка`) и вывод: проблема кода или неточность схемы.
3. **Принципы:** по каждому из 7 «соблюдается / нарушен» с `файл:строка`. Отдельно: куда реально идёт клик по фразе и кто пишет `currentSentenceId`; есть ли у текстовых книг настоящий «Источник следующей фразы» в Домене или логика живёт в `audioStore`.
4. **Чужие зоны:** таблица «кто → во что лезет → почему проблема → предложение (не правка)».
5. **Риски:** `risks` по всему проекту. Для каждого тихого (красного) случая в блоках карты: «осознанно» (принять через `ack` с причиной) или «скрытая проблема» (в отчёт, не принимать). Незнакомые файлы вне карты только посчитать.
6. **Обратная связь по карте:** что в формате, командах или сообщениях запутало, что пришлось угадывать.
7. Результат `check`.

## Для вас: что смотреть в ответе
- Не пересказывает ли агент код построчно вместо замысла.
- Не подгоняет ли схему под код молча и не утверждает ли расхождения.
- Находит ли чужие зоны сам, а не только пересказывает `zones`.
- Раздел 6 отчёта: где формат или команды запутали.
