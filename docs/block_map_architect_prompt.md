# Промпт для агента-архитектора: собрать схему по описанию функции

Скопируйте блок «Промпт» и допишите в конце описание функции или проекта. Рабочая папка: корень проекта.
Результат агента: **фрагмент `tools/blockmap/ui/model.json`** (блоки, состояния, ресурсы, сценарий) без кода проекта. Исходный код он не меняет.

## Промпт

Ты проектируешь **схему** функции, а не пишешь код. Схема описывает проект как компанию: отделы с зонами ответственности. Результат: добавления в `tools/blockmap/ui/model.json`, которые проходят `node tools/blockmap/blockmap.mjs lint` без ошибок. Сначала прочитай `docs/block_map_rules.md`, потом `node tools/blockmap/blockmap.mjs list` и `states` (чтобы не дублировать то, что уже есть).

### Модель в одном абзаце
Слои: **UI** (лицо: показывает состояние, шлёт запросы главе отдела, состояние не меняет), **State** (доска показателей: только хранит), **Domain** (отделы: каждый отвечает за свою зону, читает State/Data/Infra, пишет State, общается с другими), **Data** (архив) и **Infra** (внешний мир): работают только с Доменом. У каждого куска состояния и у каждого хранилища **один отдел-ответственный**. Начальник зовёт подчинённого, подчинённый отвечает результатом или событием, циклов нет.

### Порядок работы (не пропускай шаги)
0. **Зоны.** Раздели функцию на зоны ответственности (одна зона = одна ответственность; если ответственностей две, зон две). Для каждой зоны назначь **главу** (блок, в который обращаются из других зон). Зоны описываются в `zones`, у каждого блока поле `zone`. Из другой зоны вызывают и пишут только в главу; читать состояние можно из любой зоны.
1. **Отделы.** Выпиши зоны ответственности. На каждую один отдел с именем-ролью (Координатор, Оркестратор, Поставщик …) и одним предложением: что поставляет или решает. Мелкие функции не делай отделами: они вложены в блок-схему отдела.
2. **Состояния.** Что должен видеть пользователь. Раздели на куски (`states`), у каждого один владелец-отдел.
3. **UI.** Какие экраны показывают какие куски состояния и какие команды шлют (какому отделу-главе).
4. **Данные и внешнее.** Что хранится (Data), с чем общаемся снаружи (Infra). Для каждого ответственный отдел.
5. **Блок-схема каждого отдела** (`flows`): шаги от входа до результата, ветки для разных случаев. **Каждый шаг с данными называет источник:** `res` (кусок состояния `st_…` или ресурс), `block` (другой отдел), `via: "input"` (пришло командой) или `via: "external"`.
6. **Сценарий** (`scenarios`): блоки по слоям и стрелки между ними. Для каждой стрелки укажи `kind`: `call` (просит отдел), `write` (пишет состояние или хранилище), `data` (данные читает отдел из состояния). Ответ отдела (возврат, событие) рисуй обратной стрелкой без `kind`.
7. **Проверь:** `node tools/blockmap/blockmap.mjs lint`. Исправляй схему, пока нет ошибок (✗), и объясни каждое оставшееся предупреждение (⚠).

### Формат model.json (то, что ты добавляешь)
```json
"zones": { "z_xxx": { "title": "Название зоны", "head": "b_dom_xxx", "note": "одна ответственность" } },
"blocks": {
  "b_dom_xxx": { "title": "Координатор …", "layer": "Domain", "zone": "z_xxx", "planned": true,
                 "summary": "Одно предложение: что поставляет или решает.", "flow": "f_dom_xxx" },
  "b_state_xxx": { "title": "Состояние …", "layer": "State", "slice": "st_xxx", "planned": true, "summary": "…" }
},
"states": { "st_xxx": { "title": "…", "owner": "b_dom_xxx", "store": "useXxxStore", "fields": ["…"] } },
"flows": { "f_dom_xxx": { "title": "План: …", "nodes": [
  { "id": "s", "t": "start", "label": "команда: …", "col": 1, "row": 0, "covers": [] },
  { "id": "c1", "t": "cond", "label": "…?", "col": 1, "row": 1, "res": "st_xxx", "rw": "read", "covers": [] },
  { "id": "n1", "t": "io", "label": "записать …", "col": 1, "row": 2, "res": "st_xxx", "rw": "write", "covers": [] },
  { "id": "e1", "t": "end", "label": "готово", "col": 1, "row": 3, "covers": [] }
], "edges": [ { "from": "s", "to": "c1" }, { "from": "c1", "to": "n1", "label": "Да" }, { "from": "n1", "to": "e1" } ] } },
"scenarios": [ { "id": "sc_xxx", "title": "…", "desc": "…", "cols": { "b_ui_xxx": 0, "b_dom_xxx": 1 },
  "edges": [ { "from": "b_ui_xxx", "to": "b_dom_xxx", "label": "команда", "kind": "call" } ] } ]
```
- Типы узлов: `start`, `end` (овалы), `step` (действие), `io` (данные), `cond` (ромб, ветвление).
- Новые блоки ставь `"planned": true` (код ещё не написан), поле `file` не нужно.
- Колонки (`cols`): номер колонки блока **внутри своей зоны** (0, 1, …). Порядок зон: `zoneOrder` (подберёт `layout`).
- Колонки (`cols`), продолжение: номер колонки блока в своём слое. После всех добавлений запусти `node tools/blockmap/blockmap.mjs layout <сценарий> --apply`, чтобы стрелки пересекались меньше.

### Чего не делать
- Не менять код проекта и не придумывать файлы с кодом.
- Не создавать отдел на каждую функцию: отдел это зона ответственности.
- Не делать у состояния двух владельцев и не писать в него из UI или из чужого отдела.
- Не рисовать стрелки Data/Infra → что-либо кроме Домена, Домен → UI, State → любой вызов.
- Не оставлять шаг с данными без источника.
- Не править `bind` и `approved*` руками.

### Отчёт
1. **Отделы** (таблица: роль, зона ответственности, какие состояния владеет).
2. **Состояния** (кусок, владелец, кто читает).
3. **Сценарий словами:** кто кому что говорит, откуда каждый отдел берёт данные.
4. **Результат `lint`:** до и после (ошибки, предупреждения) и что осталось.
5. **Сомнения:** где граница между отделами была спорной, и почему выбрал так.
6. **Что было неясно в правилах или формате.**

## Для вас: как оценивать ответ
- Каждый отдел это зона ответственности, а не функция.
- У каждого состояния один владелец; UI нигде не пишет состояние.
- Каждый шаг с данными называет источник; нет данных «из воздуха».
- `lint` без ошибок. Если агент «чинил» ошибки, просто убирая стрелки, смотрите, не потерялась ли логика.
- Раздел 5 отчёта: где агенту было трудно. Это ваши правки в правилах.
