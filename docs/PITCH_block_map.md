# Block Map — проект как набор блоков с контрактами для агентов

> Рабочее название. Питч для последующей презентации. Подтверждённые факты о рынке отмечены ссылками, остальное — гипотезы и дизайн-решения.

## 1. Одной фразой

Инструмент разбивает любой проект на **блоки с типизированными контрактами входа и выхода** (как ноды в n8n), следит по хешам за тем, что контракт и код не разошлись, и отдаёт агентам не «весь репозиторий», а **готовый блок: что в него входит, что выходит, что он уже знает и что трогать нельзя**.

## 2. Проблема

1. **Агент каждый раз ориентируется заново.** Значительная часть токенов уходит на поиск «что где лежит и что от чего зависит».
2. **Агент плодит дубли.** Не зная, что нужные данные уже отдаёт другой модуль, он создаёт новый провайдер, стор или хелпер.
3. **Правки расползаются.** Нет явной границы, внутри которой агенту можно работать.
4. **Случайные поломки контрактов.** Переименование поля или выпавший кусок интерфейса обнаруживаются поздно.
5. **Тестирование неровное.** Нет единицы, которую можно проверять изолированно: «блок работает по контракту».
6. **Ручная карта устаревает.** На примере AIBookReaderWeb: в `docs/architecture` 9 схем и 84 узла поддерживаются вручную, уже есть битая ссылка на строку, висящий узел и флаги «свежих правок», которые никто не сбрасывает.

## 3. Идея

**Блок** — единица работы агента и единица проверки.

```
Блок
├─ id, название, назначение
├─ файлы блока (границы)
├─ КОНТРАКТ (источник правды)
│    ├─ входы   — схемы данных (JSON Schema / zod / TS-типы)
│    ├─ выходы  — схемы данных
│    ├─ публичные символы, которые видят другие блоки
│    └─ побочные каналы: сторы, события, IndexedDB, сеть, файлы
├─ ИЗВЛЕЧЁННОЕ (авто, из кода)  ← сравнивается с контрактом
├─ хеши: тело блока + публичный интерфейс
├─ статус: planned / in-progress / done / stale / drifted
└─ тесты блока (по контракту)
```

### Две стороны одной монеты

| | Откуда берётся | Зачем |
|---|---|---|
| **Контракт** | объявлен и утверждён (предложен LLM или человеком) | защита от случайных переименований и выпавших кусков; цель, к которой агент обязан прийти |
| **Извлечённое** | автоматически из кода | показывает, что блок реально отдаёт и принимает; сверка с контрактом выявляет дрейф |

Расхождение между ними и есть главный сигнал системы: либо код сломал контракт (ошибка), либо контракт устарел (нужно осознанное обновление).

### Блок как реестр данных

Блок публикует, какие данные у него есть. Агент перед созданием нового провайдера или стора **сначала спрашивает реестр**: «у кого уже есть эти данные?» Это закрывает вопрос источника данных и убирает дубли.

## 4. Разделение слоёв: что автоматика, что LLM

| Слой | Кто делает | Детерминированно? | Инструменты (кандидаты) |
|---|---|---|---|
| Граф файлов и импортов | авто | да | dependency-cruiser, tree-sitter |
| Публичные символы и типы на границах | авто | да | ts-morph / TS compiler API |
| Хеши тела и интерфейса блока | авто | да | git + собственный скрипт |
| Сверка контракта и извлечённого (дрейф) | авто | да | diff схем |
| Правила границ (кто что может импортировать) | авто | да | линтер / dependency-cruiser rules |
| Статусы блоков, прогресс, тесты по контракту | авто | да | CI, тест-раннер |
| Скрытые связи (сторы, события, IndexedDB) | **частично** | нет | правила-детекторы + LLM для остатка |
| Первичная нарезка на блоки | **LLM + человек** | нет | LLM по графу, человек утверждает один раз |
| Название и смысловое описание блока | **LLM** | нет | LLM |
| Проверка «изменилась ли семантика» | **агент-ревьюер** | нет | LLM на диффе интерфейса помеченных блоков |

Принцип: **LLM только там, где нужен смысл. Всё, что можно посчитать, считается.** Карта, которой агент должен доверять, не может зависеть от угадывания.

## 5. Поток работы

1. **Инициализация.** Скрипт строит граф и кандидатов в блоки. LLM группирует и называет. Человек утверждает границы один раз; результат фиксируется в манифесте в репозитории.
2. **Контракты.** Автоизвлечение предлагает черновик схем, человек или ревьюер утверждает. С этого момента контракт — источник правды.
3. **Работа агента.** Агент запрашивает блок (MCP): контракт, соседей, что затронет правка. Работает внутри границ.
4. **Коммит или правка.** Скрипт пересчитывает хеши:
   - тело блока изменилось → блок помечен «проверить»;
   - публичный интерфейс изменился → блок помечен «контракт под угрозой».
5. **Ревью.** Агент-ревьюер получает только помеченные блоки и дифф интерфейса, проверяет контракты и утверждает, что схема актуальна, либо возвращает на доработку.
6. **Визуализация.** Карта показывает, над какими блоками идёт работа, какие завершены, какие устарели.
7. **Тесты.** Каждый блок проверяется по своему контракту изолированно.

Режимы: **автономный** (агенты ведут цикл сами, человек видит карту) и **полуавтономный** (человек утверждает границы и изменения контрактов).

## 6. Доставка

- **MCP-сервер:** «дай блок», «что от него зависит», «что затронет правка символа», «у кого есть эти данные».
- **Файлы в репозитории:** манифест и контракты как JSON/Markdown, читаются любым агентом без сервера.
- **Хуки и CI:** проверка хешей на коммите, блокировка выхода за границы блока.
- **Визуальная карта:** интерактивная схема для людей по образцу уже сделанной в `docs/architecture/index.html`, но с живыми статусами.

## 7. Что уже есть на рынке и чем отличаемся

Граф кода для агентов уже делают многие: [codebase-graph-mcp](https://github.com/0xbyt4/codebase-graph-mcp), [mcp-architect](https://github.com/kannajune/mcp-architect), [codebase-memory-mcp](https://deusdata.github.io/codebase-memory-mcp/), [codegraph-ai](https://github.com/codegraph-ai/codegraph), [DependencyMCP](https://glama.ai/mcp/servers/4ndnq31gxp). Идея детерминированной карты, которой агент может доверять, подтверждена исследованием [Repository Intelligence Graph](https://arxiv.org/html/2601.10112).

Они отвечают на вопрос «что с чем связано в коде». Мы отвечаем на другой: **«что этот блок обещает миру, и сдержан ли контракт»**.

| | Существующие графы кода | Block Map |
|---|---|---|
| Единица | файл, символ, вызов | блок с контрактом |
| Источник правды | код как есть | утверждённый контракт |
| Устаревание | пересборка индекса | хеш интерфейса, статус `stale`/`drifted` |
| Скрытые каналы данных | обычно не видны | часть контракта |
| Статусы работы и тесты | нет | статусы блоков, тесты по контракту |
| Реестр данных против дублей | нет | да |

В поиске я не нашёл инструмента с объявленными блоками-контрактами и пометкой устаревания по хешу интерфейса. Поиск не исчерпывающий, перед стартом стоит повторить его по запросам «module contracts agents» и «architecture manifest».

## 8. План: первая версия

**Полигон: AIBookReaderWeb** (TS/JS, есть ручная карта для сравнения).

1. Граф и кандидаты в блоки на dependency-cruiser. Сверить с ручным `level0_overview.json`: сколько блоков совпало.
2. Извлечение публичных символов и типов через ts-morph.
3. Формат манифеста и контракта (JSON Schema).
4. Скрипт хешей и статусов, запуск в pre-commit.
5. MCP-сервер с 4 запросами из раздела 6.
6. Агент-ревьюер на помеченных блоках.
7. Визуальная карта со статусами.

Многоязычность закладывается в архитектуре: ядро (манифест, контракты, хеши, статусы, MCP) не зависит от языка, а язык подключается как **экстрактор**, возвращающий граф и публичные символы. Первый экстрактор — TS/JS, следующие через tree-sitter.

## 9. Метрики успеха

- Совпадение автонарезки с ручной картой проекта.
- Доля правок агента, выполненных внутри одного блока.
- Число дублей провайдеров и сторов до и после.
- Время и токены агента на ориентацию в задаче.
- Доля ложных срабатываний «контракт под угрозой».
- Доля случайных нарушений контракта, пойманных до слияния.

## 10. Риски и открытые вопросы

| Риск | Что делать |
|---|---|
| Скрытые связи (сторы, события, IndexedDB) не видны статическому анализу | сделать их обязательной частью контракта; правила-детекторы для Zustand, Dexie, EventEmitter |
| Ложные срабатывания на внутренних правках | хешировать интерфейс отдельно от тела |
| Слишком строгие контракты тормозят разработку | полуавтономный режим, обновление контракта одной командой с ревью |
| Нарезка на блоки спорная и субъективная | утверждение человеком один раз и фиксация в манифесте |
| Контракт и код рассинхронизируются, ревьюер «подпишет» устаревшее | ревьюер видит дифф извлечённого против контракта, а не только код |
| Рынок быстро заполняется графами кода | позиционироваться на контрактах, статусах и реестре данных, а не на графе |

**Что ещё нужно продумать:** формат контракта для сторов и событий; как версионировать контракты; как блоки вкладываются друг в друга; что делать с монорепозиториями; как соотносится с n8n-подобным визуальным редактором (только просмотр или правка карты тоже).
