# Как правильно составлять схему (сценарии, блоки, состояния)

Схема описывает проект как **компанию**: отделы с зонами ответственности. Всё строится вокруг ответственности: кто за что отвечает, кто что может делать.

## 1. Слои как устройство компании

| Слой | Роль в компании | Что может |
|---|---|---|
| **UI** | Лицо компании | Показывает состояния. Отправляет запросы **главе отдела** (в Домен). Состояние не меняет. |
| **State** | Доска показателей | Только хранит. Ничего не вызывает и не решает. Управляется только Доменом. |
| **Domain** | Отделы | Делятся по зонам ответственности. Берут данные из State, Data, Infra, работают с ними, пишут State, общаются друг с другом. |
| **Data** | Архив | Хранилище. Работает только с Доменом: Домен читает и пишет. |
| **Infra** | Внешний мир (поставщики, оборудование) | Адаптеры к внешнему. Работают только с Доменом. |

## 2. Зона ответственности (главное правило)
- **У каждого куска состояния ровно один отдел-владелец.** Только он пишет. Остальные отделы просят его вызовом.
- **У каждого хранилища и адаптера (Data/Infra) тоже один ответственный отдел.** К нему другие отделы не ходят.
- Блок = отдел = роль (Координатор, Оркестратор, Поставщик). На верхнем уровне только роли с ответственностью. Мелкая функция («получить аудио») вложена в блок-схему своего отдела, а не стоит рядом.
- Если зона ответственности большая и внутри неё есть свои подзоны, внутри создаются вложенные блоки по этим подзонам.
- Отдел сам решает, откуда ему брать данные: из State (читает), из Data (читает и пишет), из Infra (запрашивает). На схеме это стрелки, и у каждого шага блок-схемы называется источник данных.

## 2а. Зоны (вторая жёсткая рамка)
Слои идут по горизонтали («кто по роли»), **зоны по вертикали** («чья ответственность»); блок стоит на их пересечении.
- Зона это постоянная область ответственности (например, «Плеер», «Поставка озвучки»). В зоне есть **глава** (блок-вход) и подчинённые блоки, состояния и хранилища зоны.
- Блок принадлежит **ровно одной зоне**. Если у зоны две ответственности, это две зоны (у «Воспроизведения» было две: координация и плеер).
- **Из другой зоны вызывают и пишут только в главу зоны**, не в её внутренности. Чтение состояния разрешено из любой зоны.
- Общие вещи без хозяина (настройки, тема) живут в общей зоне, а не в чужой.
- Сценарий это поток, пересекающий зоны; зоны задаются один раз на проект.
- На схеме зона это цветная рамка с названием и главой; блок нельзя вытащить за свою рамку, ширину зоны можно менять.

## 3. Взаимодействие
- **Начальник зовёт подчинённого**, подчинённый отвечает результатом или событием. Циклов вызовов нет.
- UI обращается к одному отделу (главе), не к его внутренностям.
- Данные UI получает только через State (показывает то, что в состоянии).
- Data и Infra отвечают Домену результатами и событиями (колбэки, которые регистрирует Домен). Они не импортируют Домен.
- Общие типы (`types/`) можно импортировать из любого слоя.

## 4. Как строить схему по задаче (по шагам)
0. **Зоны.** Раздели проект на зоны ответственности (область = одна ответственность). В каждой назначь главу.
1. **Отделы.** В каждой зоне выпиши отделы-блоки. Для каждого одно предложение: что он поставляет или решает.
2. **Состояния.** Что должен видеть пользователь? Раздели на куски состояния. Для каждого: владелец (один отдел).
3. **UI.** Какие экраны показывают какие куски состояния и какие команды шлют (какому главе отдела).
4. **Данные.** Что хранится (Data) и с чем общаемся снаружи (Infra). У каждого ответственный отдел.
5. **Блок-схема каждого отдела.** Шаги: вход (команда или данные), откуда берёт данные (каждый шаг с данными называет источник), что решает, что пишет, кого просит. Ветки показывают разные случаи внутри отдела.
6. **Проверка.** `blockmap lint` без ошибок: слои, владельцы, источники данных, отсутствие циклов, согласованность блок-схемы со сценарием.

## 5. Версии схемы
- Схема живёт в **версии внутри вехи**: веха это цель или объём работы. Внутри вехи версия `мажор.минор.патч`.
  - **patch**: подписи, привязки к коду, принятые расхождения.
  - **minor**: новый блок, стрелка, состояние, сценарий.
  - **major**: сменился владелец, слой, удалён блок или сценарий.
- Команда `blockmap version` показывает, что изменилось с прошлого выпуска и какое увеличение нужно. `blockmap release "заметка"` выпускает версию и сохраняет снимок структуры.

## 6. Что проверяет инструмент
`lint` (схема без кода): слои на стрелках, владелец при записи, данные из ниоткуда, согласованность блок-схемы со сценарием, циклы вызовов, ответственный за хранилище.
`check` (код против схемы): стрелка подтверждена вызовом, путь не идёт в обход блока, блок достижим от входа, код блока лежит в своём слое, запись в состояние только от владельца, к ресурсу ходит только ответственный.
`states`, `reality`, `layout`, `version`: каталог состояний, реальные связи из кода, раскладка, версия.
